# Pre-Beta Code Audit — 2026-06-10

Scope: all code added since the fork point (`2fec12a`, upstream WireGuard Apple v1.0.16) through
`3a73f6e` — ~12,300 lines across the failover engine, background probes / hot spare,
tunnel-in-tunnel (TiT), Go bridge, group CRUD, widget, session history, IP discovery,
Spotlight indexing, and website infrastructure.

Method: four parallel deep-dive reviews (Go bridge, NE-side failover engine, app-side group
management, security/privacy) cross-checked against the vendored wireguard-go source
(`v0.0.0-20230209153558`) and the two design docs. The Go package was compiled
(`go build -buildmode=c-archive` passes) and the atomic.Value behavior reproduced in
isolation. All Critical/High findings were independently verified in source.

> **Status update (2026-06-10):** fixes have landed on this branch for
> C1, C2, H3, H4, H5, H6, H7, H8, H9, H10, M-Eng1, M-Eng2, M-Go1, M-App1,
> M-App3, plus L1/L6 and the smaller hot-spare guard from M-Eng4.
> Still open: H1/H2 (keychain rework for group configs), H11 (OIDC sub
> claim — infra change, needs a coordinated redeploy), M-Eng3 (monotonic
> time), M-Eng4 (handshake pre-validation before hot-spare promote),
> M-Go2/M-Go3, M-App2/4/5/6, M-Sec1–4, and the remaining Lows.

**Bottom line: do not start beta until C1, C2, and H1 are fixed.** C1 makes every
hot-spare promotion crash the Network Extension; C2 makes the *stats writer* crash the
extension within ~30s of any successful failover (and on iOS offline/online blips). Both
are small, local fixes.

## Critical

### C1. `wgProbePromote` always panics — `atomic.Value` type-consistency violation
`Sources/WireGuardKitGo/api-apple.go:246` (field), `:256` (initial store), `:322` (swap), `:503` (call site)

`swappableTunDevice.inner` is a bare `atomic.Value`. It is first `Store`d a
`*nullTunDevice` and later `Swap`ped with a `*tun.NativeTun`. `sync/atomic.Value`
requires the same *concrete* type across all stores — storing through the `tun.Device`
interface does not help, the boxed dynamic type is what is compared. Verified
empirically: this panics with `sync/atomic: swap of inconsistently typed value into
Value`. There is no `recover` between the panic and the cgo boundary, so **every
hot-spare promotion kills the Network Extension process**. Worse, the panic fires after
`setNetworkSettings` for the new config and before `wgTurnOff(oldHandle)`
(`WireGuardAdapter.swift:541`), so the documented fallback to `adapter.update()` never
runs — the process is already gone.

**Fix:** store a small concrete wrapper (`type tunHolder struct{ tun.Device }`)
consistently, or use pointer-based indirection (`atomic.Pointer`).

### C2. UInt64 underflow trap on traffic-counter regression — extension crash after any failover or iOS offline blip
`Sources/WireGuardNetworkExtension/PacketTunnelProvider.swift:353-354`,
`Sources/WireGuardKit/ConnectionHealthMonitor.swift:219-220`

Both sites compute `currentTx - previousTx` on `UInt64`, which traps fatally on
underflow. The counters genuinely regress: (a) every `adapter.update()` sends
`replace_peers=true` (`PacketTunnelSettingsGenerator.swift:51`), resetting per-peer
tx/rx to 0; (b) every iOS offline→online cycle recreates the Go device; (c) hot-spare
promotion replaces the device. `pollAndWriteStats` **never** resets
`previousStatsTxBytes`, so ≤30s after a failover the stats timer computes
`small − large` → fatal trap → total VPN drop, *caused by the failover feature working*.
The monitor's own copy computes `txDelta` at line 219 **before** the `isFirstPoll`
baseline check at line 223, so it crashes on the first poll after any device recreation
(subway, airplane-mode toggle).

**Fix:** treat regression as a reset: `let delta = current >= last ? current - last : current`
(or `subtractingReportingOverflow`), and reset both baselines whenever the device/config
is swapped.

## High

### H1. Private keys of all group members stored in plaintext in `providerConfiguration`
`Sources/WireGuardApp/Tunnel/TunnelsManager+GroupCRUD.swift:71-72` (failover),
`Sources/WireGuardApp/Tunnel/TunnelInTunnelGroup.swift:75-84` (TiT),
read back in `PacketTunnelProvider.swift:478-534`

Failover and TiT groups pack the full wg-quick configs — including `PrivateKey` and
`PresharedKey` lines — of every member as plaintext strings into
`NETunnelProviderProtocol.providerConfiguration` (`FailoverConfigs`,
`TiTOuterConfig`/`TiTInnerConfig`). That dict is persisted in the system NetworkExtension
configuration store, **not** the keychain. Upstream deliberately migrated away from
exactly this (see the comment at `NETunnelProviderProtocol+Extension.swift:62-65`). The
group's `passwordReference` is borrowed from the primary tunnel and never actually read
by the extension — it is cosmetic. Anyone who can read NE preferences (macOS admin/root,
forensic image, device backup, MDM config dump) obtains the private keys of *all*
member tunnels of every group in one place, bypassing keychain protection classes and
ACLs entirely.

**Fix:** store each member's config as its own keychain item and pack an array of
`passwordReference`s; resolve them in the extension.

### H2. Deleting a tunnel does not purge its key from groups
`Sources/WireGuardApp/Tunnel/TunnelsManager+GroupCRUD.swift:41-49`

`buildProviderConfiguration` deliberately falls back to the previously stored config when
a member can no longer be resolved. Upstream's `removeTunnel` destroys the keychain item,
but the plaintext copy of that tunnel's keys lives on inside the group's
`providerConfiguration` indefinitely (compounding H1) and is still actively used if the
group activates. Key rotation only propagates via `refreshFailoverGroupsContaining`; any
missed path leaves stale keys in use.

### H3. `deinit`/`stop()` use-after-free in ConnectionHealthMonitor
`Sources/WireGuardKit/ConnectionHealthMonitor.swift:140-142`, `165-176`

`stop()` does `workQueue.async { self.isRunning = false … }` capturing `self` strongly.
Called from `deinit`, this retains an object whose refcount already hit zero; the block
later runs against freed memory and the closing release double-deallocs. On iOS (no
`exit(0)` hack) this races process teardown on every stop of a failover group.
**Fix:** `deinit` must do synchronous cleanup (cancel timers directly), never re-enter `stop()`.

### H4. Data race on the `state` dictionary in IPC message type 1
`Sources/WireGuardNetworkExtension/PacketTunnelProvider.swift:187-224`

The captured `var state: [String: Any]` is mutated concurrently from two completion
blocks on different queues (monitor `workQueue` and adapter `workQueue`). Swift
`Dictionary` is not thread-safe; concurrent inserts can corrupt the heap and crash the
extension. The detail UI polls this message **every 2 seconds** while open. Same pattern,
lower stakes: `activeConfigIndex` is written on the monitor queue and read unsynchronized.
**Fix:** have each completion return values and merge in `group.notify` on one queue.

### H5. iOS offline kills probes but the monitor keeps stale handles — hot spare permanently dead; handle reuse can promote the wrong device
`Sources/WireGuardKit/WireGuardAdapter.swift:740-741` vs
`Sources/WireGuardKit/ConnectionHealthMonitor.swift:563`, `api-apple.go:402-413`

On iOS path-down the adapter calls `stopAllProbes()` with no callback to the monitor, so
`hotSpareHandle`/`failbackProbeHandle` stay set and `startHotSpareIfNeeded` early-returns
forever — the hot spare is never restarted after any offline blip (violates the design
doc's documented invariant). Worse: Go allocates probe handles from the lowest free
integer, so a stale handle can alias a *newer* probe; `tryHotSpareFailover` could then
promote a device running config B while applying network settings for config A →
traffic blackhole. **Fix:** notify/clear monitor probe state when probes are
force-stopped; consider monotonic handle IDs.

### H6. Failback promotion/revert failure paths corrupt `activeIndex`
`Sources/WireGuardKit/ConnectionHealthMonitor.swift:425-437`, `530-537`;
`WireGuardAdapter.swift:532-543`

When `promoteProbe` fails, the fallback `adapter.update(configurations[0])` discards its
error and unconditionally sets `activeIndex = 0`. If that update also fails (likely —
the primary recently failed), the adapter still runs the fallback config while the
monitor believes it's on primary: failback probing stops forever and the UI reports the
wrong active config. Also, `promoteProbe` applies the new config's network settings
*before* the fd lookup / `wgProbePromote` can fail, leaving routes/DNS for config A while
wireguard-go runs config B, with nothing to repair it.

### H7. TiT IPv6 UDP checksum computed over zeroed payload — IPv6-endpoint TiT never works
`Sources/WireGuardKitGo/api-apple.go:770-773`

The mandatory IPv6 UDP checksum is computed from `pkt[40:40+udpLen]` **before**
`copy(pkt[48:], payload)` runs, so it covers zeros instead of the WireGuard payload.
Every packet is checksum-invalid and silently dropped at the receiving server — IPv6
inner endpoints just look like dead peers. (Also: a computed checksum of 0x0000 must be
normalized to 0xFFFF.) **Fix:** copy payload first, then checksum.

### H8. Go `events` channels never closed — goroutine + device leak on every probe stop / TiT teardown
`Sources/WireGuardKitGo/api-apple.go:308-316`, `:618-625`

`device.RoutineTUNEventReader` only exits when `Events()` closes; neither
`swappableTunDevice.Close` nor `pipedTunDevice.Close` ever closes its channel, so each
`wgProbeOff` / `wgTurnOffTiT` (and the error paths in `wgProbeOn`/`wgTurnOnTiT`) leaks a
goroutine pinning the entire `*device.Device` graph. Background probes are **default-on**
and cycle per failback test; the NE runs under a hard memory cap (~15–50 MB on iOS), so
hours of failed-over operation accumulate until jetsam kills the extension.

### H9. Single-tunnel delete protection misses TiT groups; key destroyed out from under the group
`Sources/WireGuardApp/Tunnel/TunnelsManager.swift:411-422`

`remove(tunnel:)` checks only `FailoverConfigNames`; `removeMultiple` checks both
failover and TiT membership. The single-delete path is what iOS swipe-delete and the
detail view use. Swipe-deleting a TiT member succeeds, destroys the keychain item whose
reference the group borrows, and leaves the group permanently un-editable (compounded by
M-App1's silent-success modify). **Fix:** one-line parity with `removeMultiple`.

### H10. TiT group zip import/export round-trip completely broken
`Sources/WireGuardApp/UI/TunnelImporter.swift:114-130`,
`GroupPersistenceManager.swift`, `TunnelInTunnelGroup.swift:57`

UI-created TiT groups live only in `NETunnelProviderManager`s; nothing writes the
`tit-groups.json` sidecar — so **export silently omits every TiT group**, and **import
only writes the sidecar** (never calls `addTiTGroup`), so imported groups never appear in
the UI yet are counted as imported. Re-imports append duplicates (no dedupe), and those
phantom sidecar entries *are* exported, accumulating ghost groups in zips.
`cleanupGroups` on both group types has zero callers (dead code). **Fix:** route TiT
import/export through the manager path like failover groups; remove or wire up the sidecar.

### H11. GitHub OIDC deploy role trusts any ref in the repo
`website/infra/lib/github-oidc-stack.ts:42`

The trust policy matches `repo:org/repo:*`, and the role can assume the CDK bootstrap
deploy/file-publishing roles — whose CloudFormation exec role is typically
account-admin. Any workflow run from any branch or PR in the repo can therefore deploy
arbitrary CloudFormation. **Fix:** pin the `sub` claim to
`repo:org/repo:ref:refs/heads/main` (or a protected GitHub environment).

## Medium

### App / group management
- **M-App1. `modifyGroup` reports success on failure paths** (`TunnelsManager+GroupCRUD.swift:242-260`).
  Rename is applied in-memory and `passwordReference` mutated *before* two guards that
  bail with `completionHandler(nil)` (= success) without saving. In-memory and persisted
  state diverge until app restart; the refactor (38e3948) extended the
  `<2 configs → nil → silent no-op` behavior to failover edits.
- **M-App2. macOS `TunnelsTracker` observer bookkeeping wrong for TiT groups** (refactor
  regression, `TunnelsTracker.swift:105-152`): TiT adds insert into the *failover*
  observer array with a kind-local index; removals can drop the wrong observer or none;
  TiT groups present at launch get no observer. Menu-bar status tracking goes stale.
- **M-App3. `addGroup` has no duplicate-name check** (`GroupCRUD.swift:141-221`): zip
  re-import duplicates failover groups indefinitely; group names can collide with tunnel
  names, making name-based config sync and delete protection ambiguous.
- **M-App4. `refreshFailoverGroupsContaining` silently drops unresolvable members**
  (`TunnelsManager+Failover.swift:52-63`) — bypasses the stored-config fallback and can
  shrink a group below 2 members, making it invisible to export.
- **M-App5. Group-refresh saves bypass the iOS reactivation hack and swallow errors**
  (`TunnelsManager+Failover.swift:74-78`, `+TunnelInTunnel.swift:76-80`): editing a
  member tunnel while another tunnel is active can knock the active tunnel offline with
  nothing to bring it back; failed group saves leave stale keys/endpoints silently.
- **M-App6. Failover import degrades silently / misleading errors**
  (`TunnelImporter.swift:132-168`): missing member .confs produce a smaller group
  reported as success; every addGroup validation failure surfaces as "tunnel name empty".

### Failover engine
- **M-Eng1. Health checks keep evaluating during the legacy probe window**
  (`ConnectionHealthMonitor.swift:205-294`, `473-497`): a poll during the 15s disruptive
  probe can trigger a conflicting concurrent switch. Gate `evaluateHealth` on `!isProbing`.
- **M-Eng2. Probe device leaks on several exit paths** (`WireGuardAdapter.swift:509-525`,
  `ConnectionHealthMonitor.swift:371-389`): `promoteProbe`'s `.invalidState` guards
  return before removing the handle after the monitor already cleared its copy — the
  orphan keeps handshaking for the tunnel's life; `startProbe` completions don't re-check
  `isRunning` across `stop()`.
- **M-Eng3. Wall-clock `Date()` for all interval math** (`ConnectionHealthMonitor.swift:84,
  253-268`): sleep/wake can trigger spurious failovers; a backwards clock step disables
  failover until the clock catches up; handshake-age comparison breaks across clock steps.
  Use monotonic time.
- **M-Eng4. Hot-spare promotion not pre-validated and can target the active index**
  (`ConnectionHealthMonitor.swift:571-639`): promotes without checking the spare's
  handshake age (a session-less spare burns the 60s hold time), and a stale
  `hotSpareConfigIndex` can "fail over" to the config already active.

### Go bridge
- **M-Go1. Promoted `NativeTun` events never drained** (`api-apple.go:382`, `:494-503`):
  MTU stays at the null tun's 1420 snapshot (iOS utun is 1280); after 10 route events the
  route-listener goroutine blocks forever and `wgTurnOff` leaks it.
- **M-Go2. Handle registries are unsynchronized Go maps** (`api-apple.go:63`, `:373`,
  `:851`): safe today only because every call funnels through the adapter's single serial
  queue; any future off-queue call is a hard `fatal error: concurrent map writes`. A
  mutex costs nothing.
- **M-Go3. Double-close of the dup'd tun fd on `CreateTUNFromFile` failure**
  (`api-apple.go:494-498`, `:906-911`; inherited from upstream `:107-111`): fd-number
  reuse means the stray close can kill an unrelated live descriptor (e.g. the active
  tunnel's UDP socket) during a failed promotion.

### Security / privacy
- **M-Sec1. Always-on session history**: tunnel names, exact connect/disconnect
  timestamps, byte totals, and failover events persisted unencrypted in the app-group
  container (500 records ≈ months), no opt-out, no file-protection class, included in
  backups, readable by any non-sandboxed same-user process on macOS
  (`SessionHistoryStore.swift:47-77`). Upstream deliberately retains no history. Add an
  off switch + `.completeFileProtection` at minimum.
- **M-Sec2. Widget can show "Connected" indefinitely after the VPN drops**:
  `VPNStatusData` is written only by the app process; if the tunnel dies while the app is
  suspended, the widget keeps rendering "Connected" (`WireGuardWidget.swift:74-106`).
  Derive connectedness from the NE's `VPNTrafficData.updatedAt` heartbeat.
- **M-Sec3. Public IP logged at `.info` into the exportable log and stored in plaintext
  shared defaults** (`TunnelsManager.swift:770`, `IPDiscoverySettings.swift:38-41`):
  exported support logs contain a timestamped list of the user's exit (or real) IPs.
- **M-Sec4. IP discovery can leak the real IP**: fires on a fixed 2s delay after
  `.connected` with no re-check the tunnel is still up; split-tunnel configs whose
  AllowedIPs don't cover icanhazip always bypass the tunnel; fires on every
  reassert→connected flap; UI string doesn't disclose the third-party service. (Mitigated:
  opt-in, default off, HTTPS, correctly runs in the app process.)

## Low (abbreviated)

- TiT delete-protection alert reuses the "failover group" error text (`TunnelsManager.swift:473-476`).
- Suffix-based zip classification can silently drop a tunnel named `*.failovergroup` (`ZipImporter.swift:46-60`); group files aren't deduped.
- `modifyGroup` always restarts an active group even when nothing changed (`GroupCRUD.swift:304-307`).
- `FailoverGroupConfig` parser: header-with-no-body throws `noGroupSection`; duplicate members accepted (`FailoverGroupConfig.swift:84-86`).
- `getGroupState` returns nil during `.reasserting` — list label goes stale across failovers (`GroupCRUD.swift:353`).
- `isProbing` mutated off-queue (`ConnectionHealthMonitor.swift:507`).
- Unhealthy delegate fires every 10s poll during hold/cooldown → session-history event spam (`ConnectionHealthMonitor.swift:265`).
- `compactMap` over unparseable configs shifts indices vs `failoverConfigNames` → wrong display names in events (`PacketTunnelProvider.swift:510-529`).
- `adapter.healthMonitor` is an unsynchronized `public var` (`WireGuardAdapter.swift:69`).
- Anti-flap cooldown counts *switches*, not full cycles as documented.
- Probes can be scheduled while offline / during `temporaryShutdown` (`ConnectionHealthMonitor.swift:180-188`).
- TiT unwrap doesn't validate protocol/fragmentation/port (noise only — WG MACs reject garbage; bounds checks are correct); IPv4 wrap uses ID=0 with DF clear (fragmentation-corruption risk); asymmetric v4/v6 source-address fallbacks (`api-apple.go:716-807`).
- Notifications put user-chosen tunnel/config names on the lock screen (opt-in, default off) (`PacketTunnelProvider.swift:566-608`).
- Probe/hot-spare traffic is an observable two-server fingerprint (by design; document it).
- Session-history orphan recovery races on-demand activation (`SessionHistoryStore.swift:111-117`).

## Verified sound

- **App group ID rename (3a73f6e)** is fully consistent across all five targets'
  Info.plists, entitlements, and every consumer; no stale `com.wireguard.*` keys remain.
- **No key material in any new logging** (Swift or Go); group export formats
  (`.failovergroup.conf`, sidecar JSONs) are key-free; regular tunnels still use the
  upstream keychain path; the keychain-reference whitelist in `load()` correctly retains
  group-borrowed refs.
- **Entitlements/Info.plist deltas minimal**: only the widget's app-group entitlement;
  no ATS exceptions, background modes, or push/keychain-sharing additions. Widget has no
  keychain/NE/network access. Spotlight indexes only the static app name + generic keywords.
- **IPC surface**: length-guarded, unknown types → nil, debug force-failover/failback
  correctly `#if FAILOVER_TESTING`-gated end-to-end; messages restricted to the
  containing app.
- **Go**: package compiles; all three new `tun.Device`/`conn.Bind` implementations
  satisfy the vendored interface contracts; the swappable-read retry loop has no lost
  wakeup; TiT teardown ordering (inner before outer) cannot deadlock; `injectKeepalive`
  UAPI handling is correct; success-path fd ownership transfers cleanly; cgo
  string/pointer hygiene is fine.
- **Engine**: timer lifecycle and queue confinement are otherwise correct; rotation math
  is in-bounds with a terminating retry chain; 1-config groups never start the monitor;
  all-unhealthy cycles can't wedge; UAPI parsing tolerates malformed lines;
  `adapter.update()` toggles `reasserting` with `defer` and fails cleanly before any
  settings change on DNS errors.
- **Manager**: single-active-tunnel enforcement spans all three arrays; rename
  propagation rewrites packed names correctly and can't bypass delete protection;
  add/move/remove delegate index math is consistent on both platforms; the 38e3948
  refactor *fixed* two pre-existing gaps (cross-kind rename collisions, active-tunnel
  capture) and its delegate plumbing is correct.
